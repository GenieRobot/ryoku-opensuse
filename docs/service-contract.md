# Typed service and helper contract

Status: versioned Rust protocols, a runnable unprivileged per-user daemon, and a systemd socket-activated root helper for [issue #17](https://github.com/GenieRobot/ryoku-opensuse/issues/17), plus a fail-closed sequencing contract for [issue #20](https://github.com/GenieRobot/ryoku-opensuse/issues/20). The per-user service and helper units are packaged, but installed Tumbleweed activation, provider mutation, and recovery transactions are not yet proven or enabled.

## Protocol

`ryoku-service` defines protocol version 1 in Rust. Each envelope carries a validated bounded request ID and one typed request: capability discovery, durable operation lookup, or a named managed action. The decoder bounds input to 64 KiB, rejects unknown required fields and versions, and validates package, profile, checkpoint, request, and operation identifiers during deserialization. Responses distinguish acceptance, durable operation state, and structured errors. Operation phases are explicit, and journal transitions are restricted to `accepted → capturing → applying → verifying → succeeded`, with failure exits at each in-progress phase.

There is no generic command request. The helper protocol has a versioned, bounded envelope and four typed request variants: non-mutating action availability, linked-checkpoint verification, package transaction, and checkpoint restore. The latter three carry validated transaction/manifest references and typed package/checkpoint IDs. Unknown fields, unsupported versions, malformed IDs, empty/oversized/duplicate package lists, and frames over 64 KiB are rejected before policy dispatch. There are no paths, executable names, argv arrays, shell strings, environment variables, or arbitrary provider names. The helper currently returns only structured rejections: availability and provider requests return `unsupported` for an authorized caller; UID 0 is denied. It does not write an operation journal or invoke a provider.

`serve_operator_helper_connection` obtains `SO_PEERCRED` before parsing/dispatch, bounds the request frame, applies five-second read/write deadlines, and writes only a typed rejection response. The systemd socket is fixed at `/run/ryoku/helper.sock`, owned by root and group `ryoku-operators`, mode `0660`; administrators opt users into this group manually. The systemd-activated root helper verifies the inherited descriptor's pid/count and pathname before accepting connections. It never creates an operation record or invokes a provider. Invalid complete frames receive a generic malformed/unsupported rejection with a fixed correlation ID; truncated/closed peers are dropped without attempting to write to a disconnected socket.

## Authentication, runtime, and persistence

On Linux, `PeerIdentity::from_unix_socket` reads credentials from the connected socket using `SO_PEERCRED` through safe rustix APIs. The socket's filesystem mode gates access to the opt-in group; helper policy rejects root and uses the kernel-reported caller UID as the future per-user scope. The user daemon forwards only a typed `CheckAvailability` probe over the fixed socket. The helper accepts no user paths and does not open user configuration. Group membership is an explicit administrator decision and is not granted by package installation.

`OperationJournal` replays bounded, versioned newline JSON records from a caller-supplied already-validated file descriptor. Each legal state transition is synchronized before its in-memory state changes, so a reconnect can query the last durable state without resubmitting the action. The packaged `ryoku-service` user unit sets `XDG_STATE_HOME` to `%h/.local/state`; the executable binds `$XDG_RUNTIME_DIR/ryoku-service.sock` (mode `0600`) and stores its journal at `$XDG_STATE_HOME/ryoku/operations.log` (mode `0600` in a private per-user directory). It refuses root startup, checks directory/file ownership and permissions, rejects a live duplicate socket, applies bounded request framing and socket read/write deadlines, and authenticates clients using kernel peer credentials. It serves one request per connection. Discovery and durable status lookup are available; all `Start` requests probe helper availability and still receive a typed `unsupported` error without being journaled as accepted. A focused Rust reconnect test closes the journal after a synced status write, reopens it, and queries that replayed status through the request handler. The user unit and privileged socket are installed but not enabled by the package. A live Tumbleweed install/start/reconnect test remains outstanding.

The caller must ensure the journal file is on durable state storage and protected by one exclusive writer. The production mutation-gate entry point records and synchronizes `accepted`, `capturing`, and `applying` before invoking the apply callback; it requires a typed verified linked-generation result plus plan revalidation. The unjournaled gate helper is compiled only for unit tests, so production callers cannot bypass durable operation history through this module. The lock descriptor must refer to a service-owned file in a non-user-writable directory, and every participating writer must lock the same inode. `flock` is advisory; it does not coordinate uncooperative external tools.

The coordinator does not create or validate `/var/lib/ryoku-state`, implement checkpoint creation/read-back verification, coordinate provider-internal writers, or implement rollback. It synchronizes the phase record before each callback; a crash during or after provider work can leave `applying` or `verifying` as the last durable phase and requires explicit recovery. Its traits and test fakes prove only local callback ordering and same-inode process serialization. The `CheckpointVerifier` implementation remains a trusted integration boundary; a caller-provided boolean is not independent evidence. No provider action is run by this module.

Discovery advertises no mutation actions in this build. Known action names remain typed so the UI can present structured unsupported errors without gaining provider authority. A future executable service must report only capabilities it can actually perform after checking recovery storage and helper availability.

## Acceptance gaps

- Prove the packaged per-user service and root socket/service activation on Tumbleweed, including process restart/reconnect and stricter race-free descriptor-based validation for runtime/state paths.
- Add helper request replay protection and independently review the installed privilege boundary. This implementation uses the opt-in operator group with per-user kernel UID scoping, not a dedicated service UID.
- Test authorization with multiple real UIDs/group membership, root, malformed/stale/unsupported requests, and verify denials leave system state unchanged.
- Integrate a provider and #16's verified linked capture/publication so an accepted operation survives client disconnect and can resume/query actual durable progress.
- Connect the coordinator to durable operation phases, authorization, complete #16 capture/publication, low-space checks, cancellation boundaries, provider-level writer coordination, and post-change capture; test interruptions and recovery.
- Exercise process restart, corruption, locking, interrupted journal writes, and user configuration separation in focused tests and the disposable Tumbleweed VM.

Until those gaps pass, #17 remains open and all managed writes remain disabled.
